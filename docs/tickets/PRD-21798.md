# PRD-21798 · [Bug] ImmyBot run omits script errors

Ticket: https://app.clickup.com/t/1dfhfaq9j6z
Repo: https://github.com/MSPbotsAIFramework/immybot-mcp@main (a5abd1c)
Work branch: dev/PRD-21798
Status: frozen @ 047613e

## Requirement understanding

One line: immybot_scripts_run should return the script's error output (PowerShell error-stream / uncaught exception text) and an error indicator (e.g. `hadErrors: true`, `errors: [...]`) when a run recorded errors, while keeping ImmyBot's own `status` value unchanged.

Damon Zhou reports that running the reporter's fixture (Local script 2, `Write-Output ('TEST-ERR ' + $env:COMPUTERNAME); throw 'TEST-VPN-FAIL simulated error'`) on computer 1 via `immybot_scripts_run(scriptId=2, computerId=1, runAs=System, timeout=90, confirm=true)` returned `{"done":true,"script_id":2,"computer_id":1,"status":"Completed","output":["TEST-ERR DEV-W11-01"],"duration_ms":2120}` — standard output only, no exception text, no field marking the run as failed. The ImmyBot portal itself shows the run as `Completed` with the thrown exception recorded separately as the run's "error output" (Yasin's comment on PRD-21777, quoted verbatim below). Because the connector drops that error output, a downstream Halo note (SOP 263, Ginko flow 05) shows only normal output and a technician could believe a failing VPN install succeeded. The reporter explicitly asks that `status` keep ImmyBot's own value (do not turn `Completed` into a synthesized `Failed`); the ask is an additional field, not a status change. The requested acceptance checks that re-test the downstream Ginko flow 05 / Halo note (SOP D-10) are the reporter's own follow-up verification, not something this connector-level ticket can itself execute or claim; this design treats them as out of scope (see Non-goals) and relies on the BA-approved Scope/Done-when below instead of the raw ticket's three "Requested Acceptance Checks".

This is a rework-adjacent bug report: PRD-21665 (merged into `main`, see Current state) already fixed `immybot_scripts_run`'s request shape and added output polling for this same tool and the same underlying `adhoc-script-runs/dx` record; this ticket is the next, separate gap found on top of that fix (error output was never read from the same record), not a regression of PRD-21665's own acceptance criteria.

Authoritative scope (BA gate comment, Micus via backlog agent, 2026-11-05, `#1600390000041199`, superseding the raw ticket's own "Requested Acceptance Checks" per `legs/design.md` S1's "read_doc: conflicts resolved by the later, requester/owner comment"):

> Scope: immybot_scripts_run returns the script's error output (PowerShell error stream / uncaught exception text) and an error indicator (e.g. `hadErrors: true`, `errors: [...]`) when the run recorded errors, and keeps ImmyBot's own status value unchanged. Done when: the reporter's fixture (Local script 2, `throw 'TEST-VPN-FAIL simulated error'`) returns the exception text and `hadErrors: true`; a clean script returns `hadErrors: false`.

## Current state (every claim carries path:line, repo @ a5abd1c on main)

- `immybot_scripts_run` is defined in `src/immybot_mcp/tools/scripts.py:168-209`; it is the only tool the ticket names. It is annotated `DESTRUCTIVE` (`_common.py:39`) and gated by `confirm: true` (`scripts.py:188-189`, returning `not_confirmed(...)` when not confirmed, `_common.py:210-215`).
- **PRD-21665 history on this exact tool** (three merged commits on `main`, read via `git log --oneline -- src/immybot_mcp/tools/scripts.py`):
  1. `cfc9181` — renamed the POST body's top-level key from `script` to `body` and switched `cancellationId` to a real `uuid.uuid4()` GUID (fixed two HTTP 400s reported at the time).
  2. `55080d0` — **reverted** the `body` rename (`script` is correct; the original 400 was caused solely by the invalid `cancellationId`, which broke ASP.NET model binding for the whole request and made the unrelated `[FromBody]` parameter — itself named `body` — read back as "required"). The GUID `cancellationId` fix was kept.
  3. `60d6d33` — added the polling mechanism this ticket's fix extends: `POST scripts/run` answers `202` with an empty body and only queues the run (ImmyBot's swagger declares no response content); the run and its output land in `GET adhoc-script-runs/dx`, which the connector did not originally read.
  - This two-round correction history on the very same tool, both corrections made only after a live INT call against `mspbotsai.immy.bot`, is why this design (below) does not treat its own open question about the error field's exact name as something it can resolve by reading this repo alone.
- **Current run flow** (`scripts.py:168-209`): on `confirm: true`, the tool resolves the stored script (`get_from_catalog`, `_common.py:267-281`), builds a `payload` from `_RUN_FIELDS` (`scripts.py:58-61`), snapshots existing run ids (`_run_page`, `scripts.py:70-76`) as `seen`, `POST`s `scripts/run` with `{"script": payload, "computerId": computerId, "cancellationId": <uuid4>}`, then calls `_await_run(client, computerId, scriptId, seen, budget)` (`scripts.py:91-109`) and merges its result into `{"done": True, "script_id": scriptId, "computer_id": computerId}`.
- `_await_run` (`scripts.py:91-109`) polls `adhoc-script-runs/dx` (via `_run_page`, `scripts.py:70-76`, which calls `GET adhoc-script-runs/dx?computerId=...&requestingClientId=<client_id>&take=10&sort=...`) every `_RUN_POLL_SECONDS` (2.0s, `scripts.py:66`) until a row not in `seen` and matching `scriptId` reaches a terminal status (`scripts.py:64-65`), or the budget (`min(timeout + 10.0, _RUN_READ_TIMEOUT)`, i.e. at most 95s, `scripts.py:57`) runs out, in which case it returns the latest seen row tagged `timed_out: true`.
- **This is the bug**: `_run_result(row, status)` (`scripts.py:79-88`) copies exactly three fields out of the matched row — `status`, `output` (JSON-decoded if it is a string), and `duration_ms` (from the row's `durationMs`) — through `compact()` (`_common.py:146-147`, which only drops `None` values). Nothing else on the row is read. The row returned by `adhoc-script-runs/dx` is known (from the same function's own comment, `scripts.py:80-81`, and the test stub at `tests/test_api_client.py:425-440`) to also carry at least `id`, `scriptId`, `durationMs`, `scriptText`, `scriptPreview` — `scriptText`/`scriptPreview` are the script body and are deliberately never copied out (this is the existing mechanism behind AC2 of PRD-21665, unaffected by this ticket). Whatever field ImmyBot uses to carry a script's uncaught-exception / error-stream text on this same row is simply never read.
- `_RUN_STATUS = ("Pending", "Running", "Completed", "Failed", "Cancelled", "TimedOut", "Aborted")` (`scripts.py:64`) is ImmyBot's own run-status enum, unchanged by PRD-21665 or this ticket; the reporter's and Yasin's observation (`status: Completed` even though the script threw) is consistent with this being the vendor's own classification of "the run reached a terminal state", not an error indicator — ImmyBot does not use `Failed` for an uncaught exception inside a script body. This matches the ticket's own instruction ("Keep status as the original ImmyBot value") and PRD-21777's comment #1600390000034656 ("ImmyBot marks the error script's run as Completed, not Failed. The thrown exception is saved in the run's error output instead.").
- **No OpenAPI/swagger schema for `adhoc-script-runs` exists in this repo** (`grep -rn adhoc-script-runs` over `.py`/`.md`/`.json` returns only `README.md`, `scripts.py`, `tests/test_api_client.py` — no contract file). ImmyBot's public documentation (`www.immy.bot/documentation/reference/api-documentation/`) does not publish endpoint-level response schemas either; it states that per-endpoint schemas live only in each instance's own `https://<subdomain>.immy.bot/swagger`, which this design environment cannot reach (no vendor credentials). This is the same category of gap PRD-21665 hit twice (the `script`/`body` key name, then the need to poll `adhoc-script-runs` at all) — both were only resolved by a live call from the dev/review leg against `mspbotsai.immy.bot`, not by reading this repo or public docs. See Tech design Option analysis and Risks for how this design handles that gap without guessing a single unverifiable field name as if it were confirmed.
- Wiki: `mbp.py wiki find` returned zero hits for `immybot`, `scripts_run`, `SOP 263` (synced 2026-11-05, HEAD `c174157`) — same gap PRD-21665 recorded; the product fact base does not cover this connector.
- Related tickets: PRD-21665 (`https://app.clickup.com/t/1dfhfaq89qx`) is the immediately-prior fix to this same tool, already merged into `main` (see history above) — this ticket is its sequel, not a regression of it. PRD-21777 (`https://app.clickup.com/t/1dfhfaq9a8x`) is the fixture-creation ticket whose comments (quoted above) are this ticket's primary evidence that the error text exists on the vendor side and is simply not surfaced by the connector.

## Product design

### Goals / Non-goals

**Goals**
- `immybot_scripts_run` returns an error indicator and the script's error-stream / uncaught-exception text when the queued run's record carries one, using the exact field names the BA's Done when tests for: `hadErrors: true` and `errors: [...]`.
- A run with no recorded error returns `hadErrors: false` (and no `errors` field), with no other change to its existing response shape.
- ImmyBot's own `status` value is never altered or re-derived from `hadErrors` — `status` stays exactly what the vendor record says (e.g. `"Completed"`), per the ticket's explicit instruction and PRD-21777's comment.

**Non-goals**
- Re-testing the downstream Ginko flow 05 / SOP 263 Halo note (the raw ticket's "Requested Acceptance Check" #3) — that is the reporter's own follow-up verification once this connector ships; this design cannot execute or claim it, and the BA's Scope/Done-when (the authoritative AC source per `legs/design.md`) does not ask for it either.
- Changing `_RUN_STATUS`, the `confirm: true` gate, or any other tool's signature.
- Fixing `immybot_scripts_run_adhoc` as an explicit, separately-tested requirement — it shares `_run_result`/`_await_run` with `immybot_scripts_run` (`scripts.py:91-109,79-88`), so it incidentally gains the same error surfacing as a side effect of the shared-helper fix (see Tech design Reuse & cleanup), but no new test case is written for it since the ticket does not report a bug against it.
- Adding a new MCP tool, or a new way to fetch run history — `immybot_scripts_execution_history`/`immybot_scripts_execution_result` (`scripts.py:264-282`) are explicitly `unsupported()` today and stay that way; this ticket only changes what the existing `_run_result` copies out of a row it already fetches.

### Acceptance criteria

- **AC1**: Given the reporter's fixture (stored Local script 2, `Write-Output (...); throw 'TEST-VPN-FAIL simulated error'`) and computer 1, When an agent calls `immybot_scripts_run(scriptId=2, computerId=1, confirm=true)` and ImmyBot's run record for that run carries the thrown error text, Then the tool's response contains `hadErrors: true` and `errors` containing that error text, and `status` is still ImmyBot's own value for that run (e.g. `"Completed"`, not a synthesized `"Failed"`).
- **AC2**: Given a stored script that runs without error (e.g. script 1), When `immybot_scripts_run` is called with `confirm=true`, Then the response contains `hadErrors: false` and no `errors` field.
- **AC3**: Given any run (error or clean), When the tool's response is inspected, Then `status` is unchanged from what `_RUN_STATUS` reports for that row (AC1/AC2 together cover this; stated separately because "don't let hadErrors leak into status" is an explicit, easy-to-violate instruction from both the ticket and PRD-21777).
- **AC4**: Given the same run record that is read for `status`/`output`/`duration_ms` today, When the tool builds its response, Then no additional network call is made to get the error text — it comes from the same already-fetched `adhoc-script-runs/dx` row (guards against inventing an unverified second endpoint, see Tech design Option analysis).

### Open questions

- **[Not blocking, assumption — the central uncertainty of this ticket]** No OpenAPI/swagger schema for `adhoc-script-runs` is available to this design (see Current state); the exact field ImmyBot uses on that row to carry a script's error/exception text is not confirmed anywhere in this repo, its tests, or public ImmyBot docs. This design's assumption (Tech design §Change list) is to check a short, prioritized list of plausible field names (`error`, `errorOutput`, `exceptionMessage`, `exception`) on the row and use the first non-empty one. **This is a guess, explicitly flagged as such** — exactly the kind of assumption that PRD-21665 had to correct twice (the `script`/`body` key, then the need to poll `adhoc-script-runs` at all), both times only after a live call against `mspbotsai.immy.bot`. Dev leg must run the ticket's own reproduction (script 2 on computer 1) against the live instance before marking AC1 done; if none of the listed keys carries the text, dev leg must read the raw JSON row returned for that run, use the real key, and record that as new evidence in Self-test — not weaken AC1, and not silently drop the feature.
- **[Not blocking]** The reporter's "Requested Acceptance Checks" #3 (re-test SOP 05 D-10 and check the Halo note) is not in the BA's Done when and is not something this ticket can execute; flagged for the reporter/BA to close separately once this ships (see Non-goals).
- **[Not blocking, assumption]** `immybot_scripts_run_adhoc` will incidentally start returning `hadErrors`/`errors` too, as a side effect of fixing the shared `_run_result` helper. Not a goal, not independently tested — if the same connector-unread-error-field problem turns out to need a separate decision for ad hoc (unsaved) scripts, that would need a new ticket; nothing in the current ticket or PRD-21777 suggests the behavior should differ between the two tools.

## Tech design

### Conclusion

Extend `_run_result()` (`scripts.py:79-88`), the single place that turns a `adhoc-script-runs/dx` row into the tool's output, to also read the run's error text and compute `hadErrors`/`errors` from the same row already being polled for `status`/`output`/`duration_ms`. No new API call, no new tool, no signature change on `immybot_scripts_run`. The one open risk (confirming the real vendor field name) is explicitly handed to dev leg's live self-test, per the established pattern for this exact tool (PRD-21665's two correction rounds).

### Where the current implementation lives

See "Current state" above for the full annotated list; the one function that changes is `_run_result` (`scripts.py:79-88`), plus a new small helper next to it.

### Change list

- `src/immybot_mcp/tools/scripts.py` [modify]:
  - Add a module-level constant next to `_RUN_STATUS` (`scripts.py:64`): `_ERROR_FIELDS = ("error", "errorOutput", "exceptionMessage", "exception")` — the prioritized, explicitly-assumed candidate list from Open questions.
  - Add a small helper next to `_run_result` (`scripts.py:79`): `_run_errors(row: dict) -> list[str]`, which checks each key in `_ERROR_FIELDS` in order and returns the first non-empty value as a one-element list (string value) or as-is (already a non-empty list of strings/values coerced to `str`); returns `[]` if none of the keys are present or all are empty/`None`.
  - In `_run_result()` (`scripts.py:79-88`): call `_run_errors(row)`, and add `"hadErrors": bool(errors)` (always present, a real `bool`, never dropped by `compact()` since `False is not None`) and `"errors": errors or None` (so `compact()` drops it when the list is empty) to the dict passed through `compact()`. `status` and `output` are read exactly as today — not touched by this change (satisfies AC3).
  - No change to `immybot_scripts_run`'s or `immybot_scripts_run_adhoc`'s own bodies (`scripts.py:168-209,212-255`) — both already merge whatever `_await_run`/`_run_result` returns into their response dict, so both pick up `hadErrors`/`errors` automatically.
- `tests/test_api_client.py` [modify]:
  - Extend the `runs()` stub factory (`tests/test_api_client.py:425-440`) with an optional `error: str | None = None` parameter that, when given, adds `"error": error` to the stubbed row (using the first candidate field name from `_ERROR_FIELDS`, since the stub represents "the vendor record, however it is really shaped" for test purposes — this is the one place the design's field-name assumption becomes falsifiable by a later, cheap edit if dev leg's live check finds a different real key).
  - Add a new test asserting that when the stubbed row carries that error field, `immybot_scripts_run`'s result has `hadErrors: True` and `errors == [<the error text>]`, while `status` is still `"Completed"` (covers AC1/AC3).
  - Add a new test asserting that the existing clean-run stub (`runs()` with no `error`) now also asserts `hadErrors: False` and `"errors" not in result` (extends the existing `test_script_run_needs_confirm_and_replays_script`, `tests/test_api_client.py:443-458`, rather than adding a whole new test — covers AC2).
- `tests/contract_types.json` / `tests/test_contract_types.py` [no change expected] — `immybot_scripts_run`'s public *parameter* types are unchanged; only the shape of its string-encoded JSON *result* gains two optional keys, which these files do not pin (confirmed by reading `test_contract_types.py:1-18` and the `EXPECTED_TOOLS`/`REQUIRED` tables in `test_tools.py`, same reasoning PRD-21665's Tech design used for the same files).

### Reuse & cleanup

- **Reuse**: the already-fetched `adhoc-script-runs/dx` row (`_run_page`, `scripts.py:70-76`) and the existing `compact()` (`_common.py:146-147`) are reused unchanged; no new ImmyBot API call is added. `_RUN_STATUS`/`status` handling (`scripts.py:64-65,101`) is reused completely untouched, which is what keeps AC3 true by construction rather than by a separate check.
- **New dependencies**: none.
- **API/param shape**: `immybot_scripts_run`'s and `immybot_scripts_run_adhoc`'s public MCP parameter signatures are unchanged. Their JSON *result* gains two new optional keys (`hadErrors: bool`, `errors: list[str]`, the latter only present when non-empty) — additive, not breaking for any existing caller that ignores unknown keys.
- **In-scope cleanup**: none found — `_run_result`, `_await_run`, and the surrounding `scripts.py`/`_common.py` code are current and in active use (most of it added two days ago by PRD-21665); nothing dead is touched by this change.
- **Follow-ups (out of scope for this ticket)**: (a) if dev leg's live check finds the real vendor field is not in `_ERROR_FIELDS`, or carries richer structure (e.g. a list of per-line error entries rather than one string) than this design assumes, that is new evidence to fold into this same ticket's implementation (not a separate ticket — see Open questions), since it is still inside this ticket's scope of "surface the error text that is already on the row." (b) The reporter's Requested Acceptance Check #3 (re-test SOP 05 D-10 on Halo) — separate, downstream verification once this ships, owned by the reporter/Ginko team, not this connector ticket.

### Data & API contract

- **Outbound requests**: unchanged — `POST /api/v1/scripts/run` (`scripts.py:201-205`) and `GET /api/v1/adhoc-script-runs/dx` (`scripts.py:70-76`) are called exactly as they are today; this ticket reads one more field out of a response that is already being fetched and parsed.
- **MCP tool contract** (`immybot_scripts_run`, additive change only):
  - Before: `{"done": true, "script_id": <int>, "computer_id": <int>, "status": <string>, "output": <any>, "duration_ms": <int|null>}` (keys present only when non-`None`, via `compact()`).
  - After (error run): `{"done": true, "script_id": 2, "computer_id": 1, "status": "Completed", "output": ["TEST-ERR DEV-W11-01"], "duration_ms": <int>, "hadErrors": true, "errors": ["TEST-VPN-FAIL simulated error"]}` (exact error string depends on what the real vendor field carries — see Open questions; the field name `errors` is fixed by the BA's Done when regardless of that uncertainty).
  - After (clean run): `{"done": true, "script_id": 1, "computer_id": 1, "status": "Completed", "output": [...], "duration_ms": <int>, "hadErrors": false}` — no `errors` key.
  - `immybot_scripts_run_adhoc`'s result gains the same two optional keys, for the same reason (shared helper), with no change to its own parameters.
- **Error surfacing** (unchanged): ImmyBot API-level errors (4xx/5xx on `scripts/run` itself, not script-internal errors) still become the structured `error_envelope()` via `ImmyBotError`/`run_tool` (`_common.py:237-261`, `api_client.py:96-104`) — this ticket is entirely about script-internal errors recorded on a successfully-queued, successfully-polled run, a different path.
- No DB, no migration, no new credential fields — this repository has no database and this change adds no new ImmyBot credential requirement.

### Key flow / sequence

1. Agent calls `immybot_scripts_run(scriptId=2, computerId=1, confirm=true)`. (Unchanged through to the POST — see Current state.)
2. ImmyBot executes the script; it throws after writing output (the reporter's fixture). ImmyBot records the run as terminal with `status` unchanged (e.g. `Completed`) and — per PRD-21777's observation — stores the exception text somewhere on the run record, separate from `output`. (Vendor-side behavior, unchanged by this ticket; the connector's job is only to read what is already there.)
3. `_await_run` (`scripts.py:91-109`) polls `adhoc-script-runs/dx` as today and finds the row once it reaches a terminal status. (Unchanged.)
4. **Changed**: `_run_result(row, status)` now also calls `_run_errors(row)`, computing `hadErrors`/`errors` from the same row, in addition to `status`/`output`/`duration_ms`.
5. The tool returns `{"done": true, "script_id": 2, "computer_id": 1, "status": "Completed", "output": [...], "duration_ms": <int>, "hadErrors": true, "errors": [...]}`.

### Non-functional

- **Idempotency/concurrency**: unaffected — no change to how runs are queued, matched (`seen`, `scripts.py:200`), or polled; this ticket only changes what is read off a row already being read.
- **Performance**: unaffected — no new network call, no change to `_RUN_POLL_SECONDS`/`_RUN_READ_TIMEOUT` (`scripts.py:57,66`).
- **Security**: unaffected and, if anything, slightly improved in intent (the stated goal is to stop a technician from being misled into thinking a failed VPN install succeeded). `_run_errors()` only ever reads fields already on a row scoped to the caller's own `client_id` and `computerId` (`scripts.py:71-73`); it does not read or expose `scriptText`/`scriptPreview` (AC2 of PRD-21665, unaffected — confirmed by the Change list only touching `status`/`output`/`duration_ms`/`hadErrors`/`errors`). Credential handling is untouched (headers only, never stored, `api_client.py:39-42`).
- **Multi-tenant isolation**: unaffected — `computerId` and credentials continue to flow per-request exactly as before (`scripts.py:71-73`); no shared state is introduced.
- **Observability**: existing `logger.info("tool=%s outcome=...")` (`_common.py:260`) already logs per-call outcome without logging script output/body/credentials; this ticket adds no new logging (the error text itself is returned to the caller, which is the whole point of the fix, so there is nothing new to additionally log without duplicating the response).

### Rollout & rollback

Single-repo change in `MSPbotsAIFramework/immybot-mcp`. No DB, no feature flag — this is an additive field on an existing tool's result, not new user-facing behavior that needs staged exposure. Rollout: dev leg runs the repo's own test suite on code synced with the latest `main`, self-tests the live reproduction (script 2 / script 1 on computer 1, per Open questions), merges, and publishes to INT via `mcppub` per `mcp-track.md` §3/§4. Rollback: revert the one commit (helper + `_run_result` change + matching test updates) and re-publish INT; the server holds no persistent state.
