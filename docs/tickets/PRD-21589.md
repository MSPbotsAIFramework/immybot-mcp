## Requirement understanding

One line: Add the missing ImmyBot MCP tool `immybot_computers_set_needs_onboarding` (POST `.../computers/{id}/set-to-needs-onboarding`) so the Rewst "Assign User and Onboard Computer" flow can be migrated to MSPbots.

Per the Rewst → MSPbots migration gap list (`mspbots-gap-register.xlsx`, item 21; Rewst account "Ginko IT"), the ImmyBot MCP connector is already deployed with 68 tools but is missing one specific action: marking a computer as "needs onboarding" so a later maintenance run (`run_immy_service`) starts the onboarding flow. This gap blocks migrating the live Rewst flow `[Rewst Master v2] ImmyBot: Assign User and Onboard Computer` (evidence grade A, ~365-day execution history, Ginko IT). Success is a new tool `immybot_computers_set_needs_onboarding(computerId)` that calls `POST {instance}/api/v1/computers/{id}/set-to-needs-onboarding` and returns success, in the same shape as the existing `immybot_computers_trigger_checkin` tool.

## Product design

### Goals / Non-goals

Goals:
- Add one new MCP tool, `immybot_computers_set_needs_onboarding(computerId)`, calling `POST computers/{computerId}/set-to-needs-onboarding`, in the same shape (annotations, parameter, response envelope) as `immybot_computers_trigger_checkin`.
- Keep the new tool indistinguishable in contract style from the rest of the Computers tool group, so the gateway's tool catalog and existing agent prompts need no special-casing.

Non-goals:
- Not implementing `run_immy_service` / starting the onboarding maintenance session itself — that capability already exists (`immybot_maintenance_sessions_start`, confirm-gated). This ticket only adds the status-setter the Rewst flow calls *before* that step.
- Not changing any other Computers tool, or any other tool group.
- Not adding a corresponding "clear needs-onboarding" / revert tool — not requested, and presumably ImmyBot clears the flag itself once onboarding maintenance runs. If that assumption is wrong, that is a separate gap-register item.

### Acceptance criteria AC1..ACn

- AC1: Given a valid `computerId` and valid ImmyBot credential headers, when `immybot_computers_set_needs_onboarding` is called with that `computerId`, then the result is `{"done": true, "computer_id": <same id>, ...}` and ImmyBot received `POST computers/<id>/set-to-needs-onboarding`.
- AC2: Given ImmyBot returns a 4xx for the given `computerId` (e.g. unknown computer), when the tool is called, then the result is the standard structured error envelope (`code: invalid_argument`, `retryable: false`) — no exception reaches the caller.
- AC3: Given the request carries no ImmyBot credential headers, when the tool is called, then the result is the standard `not_configured` error envelope and no HTTP call reaches ImmyBot — the same behaviour every other tool in this connector already has.
- AC4: Given a `tools/list` request against the deployed server, then `immybot_computers_set_needs_onboarding` is listed with exactly one required parameter `computerId` (type number), a write annotation (`readOnlyHint=false`), and is reachable from `immybot_navigate("computers")`.
- AC5: Given the merged `README.md`, then the Computers row's `**write**:` group lists `immybot_computers_set_needs_onboarding`, and the "Tool count" delivery note reads 69.
- AC6: Given two different ImmyBot credential sets used concurrently, when each calls `immybot_computers_set_needs_onboarding`, then each request only ever uses its own credentials/token — this tool introduces no new credential-handling code path, so it inherits the connector's existing per-request isolation guarantee.

### Open questions

- [不阻塞/not blocking] Whether ImmyBot's `set-to-needs-onboarding` endpoint returns a JSON body or an empty success response on 2xx is unknown — the ticket only documents "2xx" as the field the Rewst flow uses, and there is no access to ImmyBot's API reference or a live instance from design. Assumption: handle it exactly like `reinventory` already does — `_parse()` (`api_client.py`) already returns `None` for an empty body or the parsed JSON if present, so no new response-shape handling is needed either way. Not blocking: this doesn't change the tool's contract.
- [已假设/assumed] Whether calling this action twice on a computer already flagged "needs onboarding" is safe to repeat (idempotent) is assumed true, mirroring `trigger_checkin`'s `idempotentHint=true` — every other computer-status action in this connector is modeled as idempotent. If the real ImmyBot API errors on a repeat call, the dev leg should flip `idempotentHint` to `false` based on the actual observed behaviour; this is a one-line annotation change, not a redesign.

## Tech design

### Conclusion

Add one tool, `immybot_computers_set_needs_onboarding`, to `src/immybot_mcp/tools/computers.py`, copying `immybot_computers_trigger_checkin`'s shape exactly (same `WRITES_IDEMPOTENT` annotation, same `ComputerId` parameter, same no-body `POST`, same `{done, computer_id, result}` response) — this is a single missing action on an already-modeled resource, so no new client method, type, or dependency is needed; the fastest way to keep it indistinguishable from its siblings is to not invent a new shape.

### Option analysis

No alternative: this connector's convention is one tool per ImmyBot endpoint, named after the verb (`trigger_checkin`, not a generic `computers_set_status`). A generic "set computer status" tool taking a status enum was considered and rejected — ImmyBot's API doesn't expose a generic status setter (only this one specific endpoint), and a generic tool would diverge from every other write tool in this connector, which are all named and shaped after one specific endpoint each. Mirroring `immybot_computers_trigger_checkin` is the only natural shape.

### Data & API contract

**ImmyBot API (called by the new tool):**
- Method: `POST`
- Path: `{instance_url}/api/v1/computers/{computerId}/set-to-needs-onboarding`
- Request body: none (matches both `trigger_checkin`'s `reinventory` call and the Rewst example in the ticket, `url_path: "computers/{{ CTX.immy_target_computer }}/set-to-needs-onboarding", method POST`, which sends no payload)
- Response: assumed 2xx with either an empty body or a small JSON object (see Open Question 1) — the tool does not need to read any particular field from the response body, it only reports that the call succeeded.
- Errors: any 4xx/5xx → `ImmyBotError` → `error_envelope(code, message, retryable)` via the existing generic path — identical contract to every other tool, nothing new to design.

**MCP tool contract (new):**
```
immybot_computers_set_needs_onboarding(computerId: int) -> str  (JSON-encoded)
```
Success: `{"done": true, "computer_id": <int>, "result": <ImmyBot's response body, or null>}`
Error: `{"error": {"code": "invalid_argument" | "not_configured" | "unauthorized" | "not_found" | "rate_limited" | "upstream_error", "message": "<text>", "retryable": <bool>}}`

**DB**: none — this connector is stateless (credentials arrive per request, never persisted; SOP requirement).

**Backward compatibility**: purely additive. A new tool name only; no existing tool's signature, annotation, or response shape changes. Any already-connected agent simply sees one more entry the next time it calls `tools/list`.

### Key flow / sequence

1. Caller (an agent, via the MCP gateway) sends an MCP `tools/call` for `immybot_computers_set_needs_onboarding` with `computerId` and the per-request ImmyBot credential headers.
2. `run_tool` resolves the request-scoped `ImmyBotClient` via `client_factory`; if credentials are missing, it returns `not_configured` immediately with no network call (AC3).
3. The tool calls `client.post(f"computers/{computerId}/set-to-needs-onboarding")`.
4. `ImmyBotClient.request` attaches the cached/fetched OAuth token and calls ImmyBot, retrying once on a 401 (token refresh) — identical to every other tool, no new logic.
5. On 2xx: the tool returns `{"done": true, "computer_id": computerId, "result": result}` (AC1).
6. On 4xx/5xx: `ImmyBotError` is raised, `run_tool` catches it, and the standard error envelope is returned (AC2).
7. Downstream (out of scope for this ticket): an agent equivalent to the Rewst flow would next call `immybot_maintenance_sessions_start` (confirm-gated) to run onboarding maintenance — mirroring the Rewst flow's two-step shape (set the flag, then `run_immy_service`).

### Non-functional

- **Idempotency & concurrency**: setting the same computer to "needs onboarding" repeatedly is expected to be safe (`idempotentHint=true`, matching `trigger_checkin`); ImmyBot is the system of record for the flag, no client-side dedup needed.
- **Performance**: a single synchronous POST, no pagination or looping; same retry/call-budget policy as every other tool (`api_client.py` `_MAX_RETRIES`, `_CALL_BUDGET_SECONDS`) — writes are retried only on a 401 (token refresh), never on 5xx/timeout, so "a write never runs twice" (`api_client.py:227` comment) holds for this tool too.
- **Security**: credentials come only from per-request headers (`X-Immybot-*`), never stored; this tool adds no new credential path, it reuses `client_factory`. No task parameters or secrets flow through this endpoint, so the existing parameter-masking logic (`mask_parameters`) is not relevant here.
- **Multi-tenant isolation**: each request is scoped to the ImmyBot tenant/instance identified by its own credential headers (the SOP's per-request isolation); `computerId` is resolved only against whatever instance those credentials point to — same boundary `immybot_computers_get` / `trigger_checkin` already have, nothing new introduced (AC6). The existing `tests/test_api_client.py::test_token_cache_is_per_credential_set` already demonstrates that different credential sets never share a cached token; this tool does not touch that code path.
- **Observability**: covered by the existing generic request log line (`immybot_api method=%s path=%s status=%s ms=%d attempt=%d`, `api_client.py:216-219`) and `run_tool`'s per-tool outcome log — no new logging needed.

- **Contract/snapshot**: `tests/test_tools.py` — `EXPECTED_TOOLS` / `WRITE_TOOLS` / the `len(tools) == 69` assertion catch any accidental signature drift; this snapshot is a deliberate breaking-change tripwire per the README's "Tool count" note, and the generic parametrized tests (`test_required_params`, `test_annotations_match_side_effects`, `test_write_tools_say_when_to_use_them`, `test_description_budget`) automatically validate the new entry once it is in the dict.
