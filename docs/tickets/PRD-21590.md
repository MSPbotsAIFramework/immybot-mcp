## Requirement understanding

One line: Add a tool to the ImmyBot MCP connector that lists a tenant's Persons (users) — id, name, email, Azure AD id — so an agent can pick a primary user, mirroring Rewst's existing "List Persons" action used by Ginko IT.

This ticket comes from the Rewst → MSPbots migration gap register (`mspbots-gap-register.xlsx`, item 22). It names a specific, already-working Rewst flow ("[Rewst Master v2] ImmyBot: List Persons", evidence grade A, Ginko IT tenant) that calls `GET {instance}/api/v1/Persons/dx?requireTotalCount=True&filter=["tenantId","=",{tenantId}]` to list the Persons of one ImmyBot tenant, then uses the result to select a primary user. The ticket is explicit about the input (`tenantId`, ImmyBot's internal tenant id, e.g. 119 for Ginko IT — not the Entra tenant id) and the six output fields the flow consumes (`id, firstName, lastName, emailAddress, tenantId, azureId`). The ticket's own "MSPbots 现状与依据" section already states the gap correctly: ImmyBot is connected (68 tools), none of them cover Persons, and the `tenants_*` tools have no persons sub-resource — so this is a genuine capability gap, not an "already available" ticket (`mcp-track.md` §2.1 / §2.6: a specific missing capability routes to normal design, not to the no-code-change path).

## Product design

### Goals / Non-goals

**Goals**
- Add one new read-only MCP tool, `immybot_persons_list`, that lists the Persons (users) of one ImmyBot tenant with the six fields the ticket names (`id, firstName, lastName, emailAddress, tenantId, azureId`), so a calling agent can present them for a human to pick a primary user — the same job Rewst's "List Persons" action already does for Ginko IT, and (since ImmyBot connections are per-instance, not per-tenant) for every tenant reachable through the same connection.
- Keep multi-tenant isolation airtight: a person belonging to a tenant the caller did not ask about must never appear in the result, even if the vendor's own `/dx` filter turns out to be as incomplete as `immybot_computers_list`'s existing tenantId handling already assumes the vendor API can be.

**Non-goals**
- No tool to create, update, or delete a Person, and no single-person "get by id" tool. The ticket's only confirmed need — and its only confirmed Rewst flow — is listing persons to pick one; nothing in the gap register or the ticket text asks for mutation or a by-id lookup, and this repo's own rule against inventing unevidenced API shapes (see Tech design §3) applies equally to inventing unevidenced tools.
- No free-text search or filter beyond `tenantId`. The ticket's "可选...filter 其它字段" describes a capability of the vendor's generic `/dx` endpoint in general, not a requirement of this ticket; nothing in the ticket names a field to filter or search by.
- No raw `skip`-based pagination exposed to the agent (see Tech design §3, Option C) — consistent with this repo's other `/dx`-grid list tools.
- No change to any existing tool's behavior, to `INSTRUCTIONS`, or to any README section beyond the new tool's row and the tool-count line (Tech design §4).

### Acceptance criteria

- **AC1**: Given an ImmyBot tenant that has one or more Persons configured (e.g. Ginko IT, tenantId 119), When an agent calls the new tool with that tenant's id, Then the response lists each person with `id`, `firstName`, `lastName`, `emailAddress`, `tenantId`, and `azureId`.
- **AC2**: Given a tenant with zero Persons, When the tool is called for that tenant, Then the response is an empty list, not an error.
- **AC3**: Given a `tenantId` ImmyBot rejects or cannot find, When the tool is called, Then the response is a structured error (the same error-envelope shape every other tool in this connector already uses), not an unhandled exception and not a silently empty list.
- **AC4**: Given a tenant with more Persons than the tool's default page size (50), When the tool is called without specifying a limit, Then the response returns at most 50 persons and signals that more exist, and the caller can ask again with a higher limit (up to 500) to see more.
- **AC5** (multi-tenant, mandatory): Given credentials valid for an ImmyBot instance that has more than one tenant, When the tool is called for tenant A, Then no person belonging to any tenant other than A is ever present in the result, even if the vendor's own tenant filter does not fully enforce this server-side.

### Open questions

- **[Not blocking, assumption]** The ticket's own evidence sends `requireTotalCount=True`; this repo's shared `dx_params()` helper defaults that flag to `False` because its two existing callers don't read a total count back. This design keeps the vendor's documented value (`True`) for this new tool and surfaces `totalCount` as an optional `total` field when the vendor includes it — if the real response omits or names the wrapper differently, the row data itself still comes through via `as_list()`'s existing fallback (see Tech design §11); only the optional `total` field would be missing. Not blocking because there is no test account to confirm the exact envelope, and the degradation is soft.
- **[Not blocking, assumption]** The endpoint path's capitalization (`Persons/dx`) is kept exactly as the ticket's only documented working example (Rewst's `url_path`). ASP.NET Core routing is normally case-insensitive, so `persons/dx` would likely also work, but there is no second source to confirm it and no reason to deviate from the one piece of evidence available.
- **[Not blocking]** No raw `skip` pagination is exposed to the agent (Tech design §3, Option C) — if a real tenant is later found to have more than 500 Persons, that is a new, named need and belongs in a follow-up ticket.

## Tech design

### Conclusion

Add one new read-only tool, `immybot_persons_list(tenantId, limit=50)`, in a new `src/immybot_mcp/tools/persons.py` module, following this repo's existing `/dx`-grid pattern (`dx_params()` + `as_list()`) already used for maintenance sessions and actions, plus the same defensive tenantId re-filter `immybot_computers_list` already applies. Register the new module in `server.py`, add it to a new `"persons"` entry in `navigation.py`'s `DOMAINS`, and add one row to `README.md`'s Tools table (bumping the documented tool count 68 → 69). No new dependency, no DB (this repo has none), no change to any existing tool's signature or behavior.

### Data & API contract

- **Outbound request (new)**: `GET /api/v1/Persons/dx?skip=0&take=<limit>&requireTotalCount=true&filter=%5B%22tenantId%22%2C%22%3D%22%2C<tenantId>%5D` via `ImmyBotClient.get()` (`api_client.py:171-172`), built as `client.get("Persons/dx", dx_params(limit, [["tenantId", "=", tenantId]]) | {"requireTotalCount": True})`. Path casing (`Persons`, capital P) follows the ticket's only documented working example; see Open questions.
- **Expected response shape** (DevExtreme grid, same family as `maintenance-sessions/dx`): `{"data": [{"id": ..., "firstName": ..., "lastName": ..., "emailAddress": ..., "tenantId": ..., "azureId": ...}, ...], "totalCount": <int>}`. `as_list()` already tolerates a bare array as a fallback, so even if the envelope differs slightly from this assumption, the row data is still read correctly.
- **Returned fields**: exactly the six named in the ticket's "返回字段" list — `id, firstName, lastName, emailAddress, tenantId, azureId` — via `_PERSON_FIELDS`/`_person()` (mirrors `tenants.py:40-44`).
- **MCP tool contract (new)**: `immybot_persons_list(tenantId: int, limit: int = 50 [1-500]) -> str` → JSON `{"persons": [...], "count": <int>, "has_more": bool, "total": <int, omitted if the vendor's response did not include totalCount>}`, or the standard structured error envelope (`error_envelope()`, `_json.py`) via `run_tool()` on any `ImmyBotError` / `ValueError` / unexpected exception — identical error contract to every other tool in this connector.
- No DB, no migration (this repo has none). No new credential field — reuses the same four `X-Immybot-*` headers every tool already requires.

### Key flow / sequence

1. Agent already knows (or first looks up via `immybot_tenants_search`) the ImmyBot tenant id, then calls `immybot_persons_list(tenantId=119)`.
2. The tool builds `dx_params(limit, [["tenantId", "=", 119]]) | {"requireTotalCount": True}` and calls `GET Persons/dx` with those query parameters.
3. ImmyBot returns a DevExtreme grid payload; `as_list()` extracts the row array regardless of whether it is wrapped in `data`.
4. The tool defensively re-filters rows to `tenantId == 119` (mirrors `computers.py:75`), in case the vendor's own filter is incomplete.
5. Each surviving row is reduced to the six `_PERSON_FIELDS`; `listing()` caps the list at `limit` and adds `count`/`has_more`.
6. The agent receives the list and shows id/name/email to the user, who picks one `id` as the primary user. Any actual "set primary user" write action, if one exists in ImmyBot, is a separate capability not requested by this ticket (see Non-goals).

### Non-functional

- **Idempotency/concurrency**: read-only `GET`, no state change; safe to call repeatedly or concurrently; introduces no new shared state (matches every other read-only tool in this connector).
- **Performance**: capped at `limit` (default 50, max 500 — the same ceiling as this repo's other `/dx`-grid list tools); one GET per call; same retry/backoff policy as every other read (`api_client.py:233-239`: GET retried on 429/5xx/network error).
- **Security**: credentials remain header-only and are never stored, same as every tool (`api_client.py` module docstring; cache keyed by a hash of the full credential set, `api_client.py:39-46`). Person records (name, email, Azure AD id) are not secret-shaped — `_SECRET_NAME` (`_common.py:109`) matches key names like password/secret/token, not `firstName`/`emailAddress` — so `mask_parameters()` does not apply; this was considered and is deliberately not used, not silently skipped.
- **Multi-tenant isolation**: the defensive client-side `tenantId` re-filter (Key flow step 4) is the explicit answer to "could a person from another tenant leak through" — it cannot, independent of whether ImmyBot's own `/dx` filter is honored server-side. This mirrors the one documented precedent in this repo where the vendor API's tenant filter was found not fully trustworthy (`computers.py:75`).
- **Observability**: reuses `run_tool()`'s existing `logger.info("tool=%s outcome=... ms=%d")` (`_common.py:261`) and `ImmyBotClient.request`'s existing `logger.info("immybot_api method=%s path=%s status=%s ...")` (`api_client.py:220-223`) — no new logging needed; no PII beyond what every other tool already logs (method/path/status, not response bodies).

### Rollout & rollback

Single-repo change in `MSPbotsAIFramework/immybot-mcp`, one new tool, no feature flag — a new MCP tool is additive and invisible to existing callers until they choose to call it (every tool is always listed, `navigation.py:14`). Rollout: dev leg implements on code synced with the latest `main`, runs the repo's test suite, merges, and publishes to INT via `mcppub` per `mcp-track.md` §3/§4. Rollback: revert the merge commit (one new file, a small additive diff in `server.py`/`navigation.py`/`README.md`, and the matching test changes) and re-publish INT; the server holds no persistent state, so there is nothing to migrate back.

### Test strategy

- Unit-test the outbound request shape with the existing `httpx.MockTransport` Recorder pattern (`tests/test_api_client.py`): assert the path is `Persons/dx`, the query's `filter` JSON-decodes to `["tenantId", "=", <id>]`, `requireTotalCount` is `"true"`, and the returned `persons` list contains exactly the six `_PERSON_FIELDS` for each stubbed row — covers AC1.
- A stub returning zero matching rows — covers AC2 (empty list, not an error).
- A stub returning an ImmyBot error response (e.g. HTTP 404) for `Persons/dx` — covers AC3 (structured error envelope, same pattern every other tool's error path is already tested for).
- A stub returning more rows than `limit` (e.g. `limit=2`, 3 stubbed rows) — covers AC4 (`has_more: true`, capped output).
- A stub returning rows for two different `tenantId` values, called with one of them — asserts only the matching tenant's rows come back — covers AC5, the mandatory multi-tenant check.
- Regression: `tests/test_tools.py::test_tool_names_are_stable`, `test_required_params`, and `test_navigate_lists_every_tool` must all still pass with the new tool counted (69 tools total, `{"tenantId"}` required, reachable via the new `"persons"` domain).
- No live-vendor-only test case this time: unlike PRD-21665, nothing in AC1–AC5 requires a real ImmyBot instance — the ticket's own evidence (sample request and the six-field output list) is enough to make the whole contract mockable with a Recorder. If dev leg has access to Ginko IT's real `mspbotsai.immy.bot` instance, one live confirmation call is a nice-to-have, not a gate (`mcp-track.md` §2.5/§3: missing vendor account access never blocks `6b`).

### Risks & dependencies

- **Risk**: the assumed response envelope (`{"data": [...], "totalCount": ...}`) is inferred from the DevExtreme convention and the ticket's own filter example, not confirmed against a live call (no test account — not a blocker per `mcp-track.md` §2.5/§3). `as_list()` already tolerates a bare array as a fallback, so even if `totalCount` or the wrapper key differs slightly, the `data[]` rows would still be read correctly; only the optional `total` field in the tool's own response would be absent — a soft degradation, not a correctness break.
- **Risk**: path casing (`Persons/dx` vs `persons/dx`) is unconfirmed beyond the ticket's one example — see Open questions; low risk, since ASP.NET routing is normally case-insensitive.
- **Dependency**: none on other tickets or repos; single repo, no cross-repo release order needed (see `Track:` line in the stub).
