## Product design

### Goals / Non-goals

**Goals**: add one new tool, `immybot_computers_delete`, that lets an AI agent permanently delete one or more ImmyBot computer records in a single call, gated by the same explicit-confirmation pattern every other destructive tool in this repo uses, so it can replace the Rewst "Decommission Workstation Assets" flow.

**Non-goals**: no change to any existing Computers tool; no new tenant-wide "delete all computers of tenant X" shortcut (the gap register's own example only ever passes one id per Rewst run; an id array is enough — nothing asks for a tenant-scoped variant); no change to how the ImmyBot agent itself is uninstalled from the physical device (deleting the record is a MSPbots/ImmyBot-side bookkeeping action, not a remote-uninstall — same scope boundary the ticket itself draws: "批量删除电脑记录（设备下线/报废）").

### Acceptance criteria AC1..AC7

- **AC1** (confirm gate): Given 1+ valid `computerIds` and no `confirm` (or `confirm: false`), When `immybot_computers_delete` is called, Then it returns a "not confirmed" response naming the action and the ids, and does **not** call the ImmyBot API.
- **AC2** (happy path): Given 1+ valid `computerIds` and `confirm: true`, When called, Then it calls `POST computers/bulk-delete` with body `{"ids": computerIds}` once, and returns a success envelope with `done: true`, the count deleted, and the ids that were requested.
- **AC3** (upstream error): Given the ImmyBot API returns a non-2xx status for the bulk-delete call (e.g. one or more ids unknown, or a 5xx), When called with `confirm: true`, Then the tool returns the repo's existing structured error envelope (`code`/`message`/`retryable`, via `ImmyBotError.to_envelope()`) — it does not swallow the failure or report partial success it cannot verify.
- **AC4** (empty input): Given `computerIds` is an empty list, When called, Then it returns an `invalid_argument` error and makes no API call.
- **AC5** (missing credentials): Given the caller's request is missing the required ImmyBot credential headers, When called, Then it returns the same `not_configured` envelope every other tool in this repo returns (inherited for free from `run_tool`/`client_factory`, `tools/_common.py`).
- **AC6** (oversized batch): Given `computerIds` has more entries than the agreed safety cap (see Tech design §3), When called, Then it returns an `invalid_argument` error telling the caller to split the request into smaller batches, and makes no API call.
- **AC7** (no extra scoping): Given `computerIds` may belong to different ImmyBot tenants under the same connection, When called with `confirm: true`, Then the tool does not add a `tenantId` filter or any other scoping beyond what ImmyBot's own API authorizes for the caller's credentials — consistent with every other id-targeted tool in this repo (`immybot_computers_get`, `_inventory`, `_deployments` all take only the id, no tenant check). This is a documented design choice, not new behavior to build.

## Tech design

### Conclusion

Add one new tool function to `src/immybot_mcp/tools/computers.py`, following the existing `DESTRUCTIVE` + `confirm: Confirm` pattern used by `immybot_deployments_trigger` and `immybot_software_install`. It calls the existing generic `ImmyBotClient.post()` against the new path `computers/bulk-delete`; no new client method, no new config, no new dependency. This is the cheapest correct option because every piece this tool needs (destructive-confirm gate, id-list parameter, post(), error envelope) already exists in the repo in the exact shape needed — this is pure composition, not new mechanism.

### Data & API contract

- **API** (outbound, ImmyBot v1, called from `ImmyBotClient.post`):
  ```
  POST {instance_url}/api/v1/computers/bulk-delete
  Body: {"ids": [123, 456]}
  Success: 2xx (body shape unverified against a real tenant — see Open Questions)
  Failure: non-2xx -> ImmyBotError(status_code, message) -> structured envelope via classify_status() (api_client.py:76-83)
  ```
- **MCP tool contract**:
  ```
  immybot_computers_delete(computerIds: int[] (1..200 items, required), confirm: bool (optional, must be true to execute))
  -> string (JSON)

  Not confirmed:
  {"done": false, "action": "Delete 2 computer record(s): 123, 456", "message": "Not done. Describe this action to the user and call again with confirm: true only after they approve it."}

  Success:
  {"done": true, "deleted_count": 2, "computer_ids": [123, 456], "result": <raw ImmyBot response or null>}

  Error (example, unknown id):
  {"error": {"code": "not_found", "message": "ImmyBot API error 404: ...", "retryable": false}}
  ```
- **DB**: none — this repo holds no database; it is a stateless HTTP-to-HTTP bridge (`README.md:9-11`, "credentials arrive on every request as HTTP headers and are never stored").
- **向后兼容**: new tool, additive only; no existing tool's name, parameters, or response shape changes. `tests/test_tools.py`'s snapshot test (`test_tool_names_are_stable`) is the repo's own backward-compat gate for the tool list and must be updated in the same change (see Change list).

### Key flow / sequence

```
Agent/Rewst -> MCP gateway -> immybot-mcp: tools/call immybot_computers_delete({computerIds:[123], confirm:false})
immybot-mcp -> Agent: {"done": false, "action": "Delete 1 computer record(s): 123", ...}
(user/flow confirms)
Agent/Rewst -> immybot-mcp: tools/call immybot_computers_delete({computerIds:[123], confirm:true})
immybot-mcp -> ImmyBot API: POST /api/v1/computers/bulk-delete {"ids":[123]}
ImmyBot API -> immybot-mcp: 2xx
immybot-mcp -> Agent: {"done": true, "deleted_count": 1, "computer_ids": [123], "result": ...}
```

### Non-functional

- **幂等与并发**: the write itself is not retried on failure (`api_client.py:232-234`: non-GET methods only retry on 429, never on 5xx/network error, so a write never silently runs twice) — same behavior every other write tool in this repo already has; no new concurrency concern introduced.
- **性能**: single HTTP call per invocation regardless of batch size (true bulk endpoint, not a loop); the `MAX_PAGE_LIMIT` (200) cap bounds the request body size and the blast radius of one accidental call.
- **安全**: credentials are read per-request from headers and never logged or cached beyond the existing SHA-256-keyed token cache (`api_client.py:44-46`, unchanged by this ticket); the confirm gate (AC1) prevents an agent from deleting records without the user explicitly approving a named, visible action — same protection every other `DESTRUCTIVE` tool in this repo relies on.
- **多租户隔离**: this is a single-tenant-per-connection connector (`README.md:10`: "credentials arrive on every request as HTTP headers and are never stored"); there is no MSPbots-platform-side tenant table to isolate against. The only tenancy concept here is the ImmyBot-side sub-tenant `tenantId` filter used by some read tools, and per AC7 this tool deliberately does not add one, matching every other id-targeted tool (`_get`, `_inventory`, `_deployments`) — ImmyBot's own API authorizes which ids a given credential set may act on.
- **可观测**: `run_tool()` already logs `tool=<name> outcome=<ok|error|...> ms=<n>` for every call (`_common.py:216,219,222,225,227`); no new logging needed, and the log line does not include the id list or any secret.

### Risks & dependencies

- **Risk**: the real `computers/bulk-delete` response shape is unverified (Open Questions). Mitigation: the tool passes the raw parsed response through under `"result"` rather than reshaping it, so an unexpected shape degrades gracefully (still visible to the caller) instead of crashing.
- **Risk**: ImmyBot may reject the whole batch if even one id is invalid (no documented partial-success semantics) — a caller deleting 50 computers where 1 id is stale would get AC3's single error for the whole call, not 49 successes + 1 failure. Mitigation: documented as an Open Question; not blocking because the gap register's own example only ever sends one id at a time.
- **Dependency**: none on another ticket or unmerged branch.
