# PRD-21665 · [Bug] ImmyBot stored-script execution fails

Ticket: https://app.clickup.com/t/1dfhfaq89qx
Repo: https://github.com/MSPbotsAIFramework/immybot-mcp@main (b61a439)
Work branch: dev/PRD-21665
Status: in progress

## Requirement understanding

One line: Fix the ImmyBot MCP tool immybot_scripts_run so a stored Local or Global script can be executed by ID without the two HTTP 400 errors (missing body field, invalid cancellationId), while run records continue to never expose the script body.

Damon Zhou reported that under SOP 263, two attempts to run a stored Local script (`immybot_scripts_run`, scriptId=1, computerId=1, confirm=true) both failed identically with HTTP 400: "The body field is required" and "cancellationId value mcp-1-1 cannot be converted to System.Guid." This blocks three Ginko flows (05 VPN script, 06 AVD installation, 11 ImmyBot software installation) and acceptance criterion 2 of PRD-20596. The reporter also asked that script content never be returned to the model or written to run records, and asked engineering to review whether the current tool guidance (review the script with `immybot_scripts_get` before running) is necessary when the script id was already approved by an administrator/workflow. The reporter's own diagnosis (add a `body` field; or use an id-based execution endpoint) is explicitly marked as unverified in the ticket; this design verifies against the code instead of taking that diagnosis at face value.

## Current state (every claim carries path:line, repo @ b61a439 on main)

- `immybot_scripts_run` is defined in `src/immybot_mcp/tools/scripts.py:114-153`. It is the only tool that runs a stored script; it is annotated `DESTRUCTIVE` (`_common.py:39`) and gated by `confirm: true` (`scripts.py:122,134-135`).
- The confirm-gate preview (`confirm` not `True`) returns `not_confirmed(...)` (`_common.py:210-215`), which only ever includes `action` (a free-text label built from scriptId/name/computerId/runAs), never the script's `action` field (the actual script source) — this is the existing mechanism behind AC2 below, not something this ticket adds.
- When `confirm: true`, the tool looks up the stored script via `get_from_catalog(client, "scripts", scriptId, databaseType)` (`scripts.py:131`, defined at `_common.py:267-281`), which tries the `Local` catalog then `Global` when `databaseType` is not given (`_common.py:271`), issuing `GET scripts/local/{id}` or `GET scripts/global/{id}`.
- It builds a `payload` dict from a fixed set of fields read off the stored script record (`_RUN_FIELDS` at `scripts.py:53-56`: `id, name, action, databaseType, filterScriptMode, outputType, scriptCategory, scriptLanguage, scriptExecutionContext`), then overrides `databaseType`, `timeout`, `parameterOverrides`, `variables`, and `scriptExecutionContext` (`scripts.py:136-145`).
- **Bug 1 — wrong top-level key.** The POST body sent to ImmyBot is `{"script": payload, "computerId": computerId, "cancellationId": ...}` (`scripts.py:146-150`). The live ImmyBot instance returned `HTTP 400 "The body field is required"` for exactly this shape (ticket "Error Message" section) — the API does not recognize a `script` key at the top level and instead requires one named `body`.
- **Bug 2 — cancellationId is not a GUID.** `scripts.py:148` builds `cancellationId` as `f"mcp-{scriptId}-{computerId}"` (e.g. `mcp-1-1`), a plain string. The live instance returned `HTTP 400 "cancellationId value mcp-1-1 cannot be converted to System.Guid."` — ImmyBot requires an actual GUID. `uuid.uuid4()` is already used elsewhere in this codebase for a similar purpose (`server.py:18,128`, request-id generation), so a real UUID is a conventional, available fix, not a new dependency.
- `ImmyBotClient.request` (`api_client.py:186-245`) does not retry non-GET requests other than on 429 (`api_client.py:233`), so a 400 on `scripts/run` is surfaced once, as‑is, via `ImmyBotError` → `to_envelope()` (`api_client.py:96-104`) → `_error_message()` (`api_client.py:292-316`), which is how the reporter was able to quote ImmyBot's literal error text. This error-surfacing path is unchanged by this design; it is also what will show any new vendor error if the fix below is incomplete (see Risks, Tech design §11).
- The tool's docstring (`scripts.py:124-128`) currently reads: "Needs confirm: true. Executes code on the endpoint. Only when the user explicitly asks; review the script first with immybot_scripts_get." This is advisory text read by the calling agent, not an enforced precondition — `immybot_scripts_get` is never actually called by `immybot_scripts_run`.
- Wiki: `mbp.py wiki find` returned zero hits for `immybot`, `scripts_run`, and `SOP 263` (synced 2026-10-29, HEAD `7554427`) — the product fact base does not cover this connector yet. No ProductDocs page exists to verify "what the user sees today" against; this design relies on the code and the ticket's own reproduction (actual HTTP responses from the live instance), not wiki.
- Related tickets: PRD-20596 acceptance criterion 2 is blocked on this fix (ticket text; not independently reviewed, out of scope). PRD-21587 is explicitly distinguished by the reporter as unrelated ad-hoc/new-script tooling.

## Product design

### Goals / Non-goals

**Goals**
- `immybot_scripts_run` successfully executes a stored script by ID on both the Local and Global catalogs when called with `confirm: true`, without the two reported HTTP 400 errors.
- Run records (the confirm-preview and the final result) continue to never contain the script's source/body text — only id, name, status/output.
- `cancellationId` is a syntactically valid GUID on every call.

**Non-goals**
- Adding a new tool or a new way to select/execute scripts (the reporter's "use an endpoint that executes by ID" suggestion is not adopted — see Tech design §3, no such endpoint is evidenced in this repo).
- Changing the `confirm: true` gate or who may call this tool.
- Fixing Ginko flows 06 (AVD installation) or 11 (software installation) — there is no evidence in this ticket that they call `immybot_scripts_run`; see Open questions.
- A broader redesign of confirmation UX across all `DESTRUCTIVE` tools — only this tool's docstring wording is touched (AC5).

### Acceptance criteria

- **AC1**: Given a stored Local script (e.g. scriptId=1, "MSPbots VPN stand-in test") and an online computer (e.g. computerId=1 / DEV-W11-01), When an agent calls `immybot_scripts_run(scriptId=1, computerId=1, confirm=true)` under SOP 263, Then the call does not fail with HTTP 400 for a missing body field or an invalid cancellationId, and the tool returns `done: true` with the script's actual output (expected to contain `TEST-VPN-OK DEV-W11-01` for this specific script).
- **AC2**: Given any call to `immybot_scripts_run` (preview or executed), When the tool's response is inspected, Then it never contains the script's source/action text — only `scriptId`/`computerId`/`done`/`output` (or, for the unconfirmed preview, `action`/`message`, where `action` is the free-text label, not the script body).
- **AC3**: Given a stored Global script id, When `immybot_scripts_run` is called with `confirm=true` (with or without an explicit `databaseType: "Global"`), Then it executes the same way as a Local script (reusing the existing Local→Global lookup).
- **AC4**: Given any `scriptId`/`computerId` pair, When the tool builds the outbound request to ImmyBot, Then `cancellationId` is a valid RFC 4122 GUID string, not a template string like `mcp-{scriptId}-{computerId}`.
- **AC5** (minor): Given a script id that was already approved by an administrator or a pre-reviewed workflow (the reporter's "05 skill" example, where form submission is the request and approval), When the calling agent reads the tool's description, Then it is told that calling `immybot_scripts_get` first is optional in that case — the `confirm: true` requirement itself is unchanged.

### Open questions

- **[Not blocking, assumption]** The live error only names the field `body` as missing; this repo holds no OpenAPI/vendor spec to cross-check the full expected shape, so renaming the top-level key from `script` to `body` (keeping its contents unchanged) is the design's assumption of the minimal fix (see Tech design §3/§11). If the live SOP 263 call still 400s after this change, that is new evidence for the next iteration — dev leg must not weaken AC1 to make the tests pass; it must report the new error text.
- **[Not blocking]** Ginko flows 06 and 11 are listed as blocked by the ticket but nothing in the ticket or this repo shows they call `immybot_scripts_run`; if they still fail after this ships, they likely need a separate ticket against whichever tool they actually call (e.g. `immybot_software_install` / deployment tools).
- **[Not blocking]** AC5 is scoped to a one-line docstring clarification, not a redesign of the approval flow; a deeper review (if still wanted) is a separate, larger ticket.

## Tech design

### Conclusion

Two-line functional fix in `immybot_scripts_run`'s request construction (`scripts.py`): (1) generate `cancellationId` with `uuid.uuid4()` instead of a template string; (2) send the script record under the top-level key `body` instead of `script`, matching ImmyBot's literal "The body field is required" error. No new dependencies, no public tool-signature change, no DB (this repo has none).

### Where the current implementation lives

See "Current state" above for the full annotated list; the two lines that change are `scripts.py:146-150` (body key) and `scripts.py:148` (cancellationId).

### Data & API contract

- **Outbound request** (ImmyBot API, path unchanged: `POST /api/v1/scripts/run`, via `ImmyBotClient.post` at `api_client.py:174-175`):
  - Before (buggy): `{"script": {id, name, action, databaseType, filterScriptMode, outputType, scriptCategory, scriptLanguage, scriptExecutionContext, timeout, parameterOverrides, variables}, "computerId": <int>, "cancellationId": "mcp-<scriptId>-<computerId>"}`
  - After (fixed): `{"body": {...same inner record, unchanged...}, "computerId": <int>, "cancellationId": "<uuid4 string>"}` — e.g. `"cancellationId": "3fa85f64-5717-4562-b3fc-2c963f66afa6"`.
- **MCP tool contract** (unchanged): `immybot_scripts_run(scriptId: int, computerId: int, parameters?: dict, timeout?: int[1-90]=30, runAs?: "System"|"User"="System", databaseType?: "Global"|"Local", confirm?: bool) -> str` — a JSON-encoded result (`{"done": true, "script_id", "computer_id", "output"}`) or the structured error envelope from `error_envelope()` (`_json.py`) when `ImmyBotError`/`ValueError`/unexpected exceptions occur (`_common.py:237-264`, unchanged).
- **Error surfacing** (unchanged): any ImmyBot 4xx still becomes an `invalid_argument` envelope carrying the vendor's literal message (`api_client.py:96-104,243-245,292-316`). If the corrected request shape is still rejected on the live instance, dev leg's self-test will see the vendor's new exact error text rather than a silent pass.
- No DB, no migration, no new credential fields — this repository has no database and this change adds no new ImmyBot credential requirement.

### Key flow / sequence

1. Agent calls `immybot_scripts_run(scriptId=1, computerId=1, confirm=false or omitted)` → `not_confirmed(...)` returns a preview (id/name/computer/runAs only); no API call is made. (Unchanged.)
2. After the user approves, the agent calls again with `confirm=true` → `get_from_catalog(client, "scripts", 1, databaseType)` resolves the script from Local (or Global). (Unchanged.)
3. The tool builds `payload` from the resolved script record (`_RUN_FIELDS` + overrides). (Unchanged.)
4. The tool POSTs `scripts/run` with `{"body": payload, "computerId": 1, "cancellationId": <fresh uuid4>}`. (Changed: key name `body`, real GUID.)
5. ImmyBot executes the script on the target computer and streams back output within `_RUN_READ_TIMEOUT` (95s). (Unchanged.)
6. The tool returns `{"done": true, "script_id": 1, "computer_id": 1, "output": <raw output>}`. (Unchanged shape.)

### Non-functional

- **Idempotency/concurrency**: today's `cancellationId` (`mcp-{scriptId}-{computerId}`) is identical across any two concurrent runs of the same script on the same computer — a latent correctness issue beyond the reported 400, since ImmyBot could treat two independent runs as sharing one cancellation token. Switching to `uuid.uuid4()` per call fixes this as a side effect. The POST is not retried on failure (`api_client.py:233`, retry is GET-only except for 429), so a script is never silently run twice by this client.
- **Performance**: unchanged — same `_RUN_READ_TIMEOUT=95.0` budget and the same retry policy.
- **Security**: unchanged credential handling (headers only, never stored — `api_client.py:39-42`). Script source continues to flow only `ImmyBot → process memory → "output" field of the result`; the script's own `action` text is never echoed back to the caller in the preview or the result (AC2), as it is today.
- **Multi-tenant isolation**: unaffected — `computerId` and credentials continue to flow per-request exactly as before; no shared state is introduced by this change.
- **Observability**: existing `logger.info("immybot_api method=%s path=%s status=%s ...")` (`api_client.py:220-223`) and `logger.info("tool=%s outcome=...")` (`_common.py:261`) already log status/outcome per call without logging the script body or credentials; no new logging is needed.
