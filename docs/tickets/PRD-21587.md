## Requirement understanding

One line: Add an ImmyBot MCP tool that sends an inline PowerShell script straight to a specified computer and runs it immediately, returning its output, without first saving the script to the catalog.

This is item 19 of the Rewst → MSPbots migration gap register (account "Ginko IT"). The reporter's own Rewst flows (`RMM-ImmyBot: Run Powershell on Org DC`, `Deploy Azure VPN`, `Immybot: Run Powershell`) call ImmyBot's `immybot.run_ad_hoc_script` action, which posts an inline script body straight to `POST /api/v1/scripts/run` with `computerId` and `script.action` — no saved-script id involved. Today's `immybot_scripts_run` MCP tool only runs a script that already exists in the Local/Global catalog (it requires `scriptId`), so there is no MCP-side equivalent of Rewst's ad-hoc path. The reporter names two possible tool names (`immybot_scripts_run_adhoc` or `scripts_create`) and lists the fields their own Rewst action sends, but does not claim that payload shape has been verified against the current MCP server's own request-building code — this design verifies against this repo's code and its most recent related fix instead of taking the reporter's payload at face value (see Current state).

## Current state (every claim carries path:line, repo @ cfc9181 on main)

- `immybot_scripts_run` is the only script-execution tool today (`src/immybot_mcp/tools/scripts.py:115-155`). It requires a catalog `scriptId` (`scripts.py:117`), looks the script up with `get_from_catalog(client, "scripts", scriptId, databaseType)` (`scripts.py:131`, Local then Global fallback at `_common.py:267-281`), and only then builds the outbound request — there is no path to run text that was never saved.
- **The outbound wire contract for `/scripts/run` was fixed and verified against the live instance three tickets before this one, PRD-21665** (`docs/tickets/PRD-21665.md`, frozen @ `27ca902`, merged into `main` at `cfc9181`): the POST body must be `{"body": <script record>, "computerId": <int>, "cancellationId": "<uuid4>"}` — a top-level key named `script` gets `HTTP 400 "The body field is required"`, and a non-GUID `cancellationId` gets `HTTP 400 "cancellationId value ... cannot be converted to System.Guid."` (both quoted from the live instance in that ticket). The current code already sends the fixed shape (`scripts.py:146-150`): `uuid.uuid4()` for `cancellationId`, the script record under `"body"`.
- The script record ("body") that `immybot_scripts_run` sends for a *stored* script is built from `_RUN_FIELDS` (`scripts.py:54-57`): `id, name, action, databaseType, filterScriptMode, outputType, scriptCategory, scriptLanguage, scriptExecutionContext`, copied verbatim off the catalog GET response, then `databaseType`, `timeout`, `parameterOverrides`, `variables`, and (when `runAs="User"`) `scriptExecutionContext` are overridden (`scripts.py:136-147`). None of this is reachable without a `scriptId` — there is no code path today that builds this record from caller-supplied text instead of a catalog fetch.
- The confirm-gate preview (`confirm` not `True`) returns `not_confirmed(...)` (`_common.py:210-215`), which for `immybot_scripts_run` only ever includes a free-text label built from `scriptId`/`name`/`computerId`/`runAs` — never the script's actual `action` text. That design relies on the agent having a separate way to review the script first (`immybot_scripts_get`, `scripts.py:91-99`, by `scriptId`). **An ad-hoc tool has no `scriptId` and no catalog record, so this exact preview shape would give a human approver nothing to review** — this is a design decision point addressed below (AC2).
- `immybot_scripts_validate` (`scripts.py:184-194`) already accepts free-form script `content` + `language` (`Literal["PowerShell", "CommandLine"]`, `scripts.py:50`) and posts to `scripts/syntax-check` — this is the existing precedent in this repo for a tool that takes inline script text as a parameter (reused below for parameter naming and typing).
- `EXPECTED_TOOLS` in `tests/test_tools.py:30-99` pins the full `tools/list` snapshot (68 tools, `test_tools.py:130`) as a public contract; adding a tool here is an addition to that pin, not a change to any existing entry.
- Wiki: `mbp.py wiki find immybot` / `ImmyBot` / `scripts_run` all returned "no hits" (synced 2026-10-30, HEAD `bd441af`, v20261030.0410) — the product fact base does not cover this connector at all yet. No ProductDocs page exists to verify "what the user sees today" against; this design relies on the code and the ticket's own gap-register entry, not wiki.
- ImmyBot's own API reference (`https://www.immy.bot/documentation/reference/api-documentation/`, fetched 2026-10-30) confirms there is no public, static spec for `/scripts/run`'s exact body shape — it points to a **per-tenant** Swagger UI at `https://<subdomain>.immy.bot/swagger`, which needs a live credentialed instance DEV01 does not have in this environment. The reporter's own payload example (`{"script":{"name":...,"action":...,"scriptLanguage":2},"computerId":...}`) is explicitly the *old, unfixed* top-level key (`"script"`, not `"body"`) that PRD-21665 proved the live instance rejects — so it is evidence of what Rewst historically sent, not of the currently-correct contract. See Open questions.

## Product design

### Goals / Non-goals

**Goals**
- A new MCP tool lets an agent run inline PowerShell (or CommandLine) script text on one computer immediately, without saving it to the ImmyBot script catalog first — closing the gap the reporter's three Ginko Rewst flows rely on.
- The new tool reuses the exact `/scripts/run` wire contract PRD-21665 verified for stored scripts (`body` key, real-GUID `cancellationId`) rather than inventing a second, unverified shape.
- Because there is no catalog id to review beforehand, the confirmation preview itself must show enough of the script for a human to approve it.

**Non-goals**
- Not persisting the ad-hoc script to the catalog. The reporter's alternative name `scripts_create` is not adopted: "create" would imply saving a reusable catalog entry, which is not what the three cited Rewst flows do and not what this ticket asks for.
- Not broadcasting a script to a whole tenant. The ticket's optional `tenantId` field is not implemented — this tool stays scoped to one `computerId`, matching `immybot_scripts_run`'s existing scope; no evidence in this repo of a tenant-wide ad-hoc run endpoint.
- Not adding a separate `variables` parameter. `immybot_scripts_run` already hardcodes `"variables": {}` (`scripts.py:142`) regardless of caller input; the new tool mirrors that unchanged.
- Not changing `immybot_scripts_run`, its parameters, or its confirm-preview behavior at all.

### Acceptance criteria

- **AC1**: Given a reachable computer id and inline script text, When an agent calls the new tool with that `computerId`, `content`, and `confirm: true`, Then the script executes on that computer now and the tool returns `done: true` with the script's output — without the script ever having been saved to the catalog.
- **AC2**: Given `confirm` omitted or `false`, When the tool is called, Then no request reaches ImmyBot; the tool returns a not-done preview naming the computer, language and `runAs`, plus a bounded excerpt of the script (the full text up to 200 characters, or the first 200 characters followed by `...` for anything longer) — because there is no catalog id a human could review separately first (unlike `immybot_scripts_run` + `immybot_scripts_get`).
- **AC3**: Given `language="CommandLine"` instead of the default `"PowerShell"`, When the tool runs confirmed, Then the outbound request's script language reflects `"CommandLine"`, not a hardcoded default.
- **AC4**: Given any confirmed call, When the outbound HTTP request to ImmyBot is inspected, Then it POSTs to `scripts/run` with the script payload under the top-level `body` key (never `script`) and a `cancellationId` that is a real RFC 4122 GUID — the same contract PRD-21665 verified against the live instance, reused rather than re-derived.
- **AC5**: Given empty script content, When the tool is called, Then the call is rejected before any outbound request to ImmyBot is made — the same `min_length=1` pattern already enforced on `immybot_scripts_validate`'s `content` parameter.
- **AC6**: Given `name`, `outputType`, `timeout`, `runAs`, `parameters` are supplied or omitted, When the tool builds its request, Then: `name` labels the run in ImmyBot's own run history (default `"Ad hoc script (MCP)"` when omitted); `outputType` is `"Object"` or `"Table"` (default `"Object"`); `timeout` is 1-90 seconds (default 30, the same ceiling `immybot_scripts_run` already uses); `runAs="User"` maps to `scriptExecutionContext="CurrentUser"` and the default `"System"` keeps `"System"` (identical mapping to `immybot_scripts_run`, `scripts.py:144-147`); `parameters` becomes `parameterOverrides` (default `{}`).
- **AC7**: Given any call (preview or executed), When the server logs it, Then the log line records only the tool name, outcome and duration — the same existing `logger.info("tool=%s outcome=...")` pattern (`_common.py:261`) — and never the script's full text.

### Open questions

- **[Not blocking, assumption]** The exact set of fields ImmyBot's `/scripts/run` endpoint accepts in a `body` that has no catalog `id` is not directly evidenced anywhere in this repo — there is no vendor OpenAPI spec, and the per-tenant Swagger UI needs a live credentialed instance DEV01 does not have. This design's assumption (Tech design §3/§Data contract) is the minimal one: reuse the same inner-record shape already proven to work for stored scripts (`action`, `scriptLanguage`, `outputType`, `scriptExecutionContext`, `timeout`, `parameterOverrides`, `variables`, plus `name`), simply omitting the catalog-only fields (`id`, `databaseType`, `filterScriptMode`, `scriptCategory`) that don't apply to inline text. If the live instance 400s for a different missing or unexpected field once a real account is available, that is new evidence for the next iteration — dev leg must report the new vendor error text rather than guessing further or weakening AC1.
- **[Not blocking]** AC1/AC3's live execution can only be confirmed against a real ImmyBot instance (e.g. `mspbotsai.immy.bot` used in PRD-21665, or Ginko's own instance). Per `mcp-track.md` §2.5/§3 a missing vendor account does not block `6b`.

## Tech design

### Conclusion

Add one new MCP tool, `immybot_scripts_run_adhoc`, to `src/immybot_mcp/tools/scripts.py`, next to the existing `immybot_scripts_run`. It reuses the exact `/scripts/run` POST contract PRD-21665 fixed and verified (top-level `body` + `computerId` + a real-GUID `cancellationId`), but builds the inner `body` record directly from the tool's own parameters instead of fetching one from the Local/Global catalog. No new dependencies, no change to `immybot_scripts_run`, no DB (this repo has none).

See "Current state" above for the full annotated list. ### Data & API contract

- **Outbound request** (ImmyBot API, `POST /api/v1/scripts/run`, via `ImmyBotClient.post`, unchanged path): `{"body": {"name": <str>, "action": <content>, "scriptLanguage": "PowerShell"|"CommandLine", "outputType": "Object"|"Table", "scriptExecutionContext": "System"|"CurrentUser", "timeout": <int 1-90>, "parameterOverrides": <dict>, "variables": {}}, "computerId": <int>, "cancellationId": "<uuid4 string>"}`.
- **MCP tool contract (new)**: `immybot_scripts_run_adhoc(computerId: int, content: str, language?: "PowerShell"|"CommandLine" = "PowerShell", name?: str, outputType?: "Object"|"Table" = "Object", parameters?: dict, timeout?: int[1-90] = 30, runAs?: "System"|"User" = "System", confirm?: bool) -> str` — JSON `{"done": true, "computer_id", "output"}` on success, or the structured error envelope (`error_envelope()`, `_json.py`) from `run_tool()` on `ImmyBotError`/`ValueError`/unexpected exceptions (`_common.py:237-264`, unchanged).
- **Error surfacing** (unchanged): any ImmyBot 4xx becomes an `invalid_argument` envelope carrying the vendor's literal message (`api_client.py:96-104,243-245,292-316`) — if the inferred id-less `body` shape is rejected on the live instance, dev leg's self-test will see the vendor's new exact error text.
- No DB, no migration, no new credential fields — same four ImmyBot headers (`X-Immybot-Instance-Subdomain`, `X-Immybot-Tenant-Id`, `X-Immybot-Client-Id`, `X-Immybot-Client-Secret`) as every other tool.

### Key flow / sequence

1. Agent calls `immybot_scripts_run_adhoc(computerId=7, content="<script>", confirm=false or omitted)` → `not_confirmed(...)` returns a preview with a ≤200-character excerpt; no API call is made.
2. After the user approves, the agent calls again with `confirm: true` → the tool builds `payload` directly from its own parameters (no catalog GET — the key difference from `immybot_scripts_run`).
3. The tool POSTs `scripts/run` with `{"body": payload, "computerId": 7, "cancellationId": <fresh uuid4>}`.
4. ImmyBot executes the script on the target computer and streams back output within `_RUN_READ_TIMEOUT` (95s).
5. The tool returns `{"done": true, "computer_id": 7, "output": <raw output>}`.

### Non-functional

- **Idempotency/concurrency**: a fresh `uuid.uuid4()` per call (same pattern PRD-21665 established for `immybot_scripts_run`) means two concurrent ad-hoc runs never share a cancellation token. The POST is not retried on failure (`api_client.py:233`, retry is GET-only except for 429), so a script is never silently re-run by this client.
- **Performance**: unchanged budget — same `_RUN_READ_TIMEOUT=95.0` and the same retry policy as every other write tool.
- **Security**: credential handling is unchanged (headers only, never stored, `api_client.py:39-42`). The confirmation preview's excerpt (≤200 chars) is the only place script content appears in a tool response besides the output of actually running it — and the calling agent already holds the full text (it supplied `content`), so this is not a new disclosure channel, only a bounded echo-back for a human approver, analogous to what a chat UI would already show if a person pasted the same script themselves. Logs continue to record only tool name/outcome/duration (`_common.py:261`), never script text, for both the preview and the executed path.
- **Multi-tenant isolation**: unaffected — single `computerId` per call, credentials flow per-request exactly as for every other tool; no shared state is introduced. (This repo's trust model scopes an entire ImmyBot instance to one set of request headers; there is no per-computer/per-tenant ownership check anywhere else in this server for this new tool to be inconsistent with — see `immybot_computers_get` etc., unchanged.)
- **Observability**: existing `logger.info("immybot_api method=%s path=%s status=%s ...")` (`api_client.py:220-223`) and `logger.info("tool=%s outcome=...")` (`_common.py:261`) already log status/outcome per call without logging body content or credentials; no new logging is needed for the new tool to be covered.

### Test strategy

- Unit-test the outbound request shape with the existing fake-HTTP-recorder pattern (`tests/test_api_client.py`), covering AC1 (end-to-end wire shape + result), AC3 (language), AC4 (`body` key + real-GUID `cancellationId`), AC6 (defaults and overrides) — all without a live ImmyBot instance.
- Unit-test the confirm-gate preview and its excerpt behavior for a short script (≤200 chars, no truncation) and a long one (>200 chars, truncated with `...`) — covers AC2.
- Unit-test that empty content never reaches an HTTP call — covers AC5.
- Unit-test (via `caplog` or an equivalent log-capture fixture) that the script's full text never appears in any emitted log record across a preview + an executed call — covers AC7.
- Unit-test that special characters commonly found in PowerShell (quotes, backticks, newlines — e.g. the reporter's own "download ScriptURL then `iex`" pattern) survive verbatim into the outbound request body, unmangled by JSON encoding or excerpt truncation.
- AC1/AC3's literal live-execution behavior can only be confirmed against a real ImmyBot instance; dev leg's self-test should attempt this if a reachable account/instance is available (e.g. the `mspbotsai.immy.bot` instance used in PRD-21665, or a Ginko-specific one), and record it as "needs a real vendor account" otherwise — per `mcp-track.md` §2.5/§3, a missing vendor account does not block `6b`.
- Regression: `tests/test_tools.py`'s full `EXPECTED_TOOLS` snapshot (now 69 tools) and `tests/test_contract_types.py`'s type pins are both expected to pass with one new entry each; every existing tool's entry, including `immybot_scripts_run`'s, stays unchanged.
