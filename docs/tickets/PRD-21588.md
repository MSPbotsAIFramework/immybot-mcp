## Requirement understanding

One line: Add a tool to the ImmyBot MCP connector that lets an agent set a computer's primary user (person), optionally also setting onboarding status and additional linked users, matching ImmyBot's `PUT /api/v1/computers/{id}` endpoint and the Rewst flow "ImmyBot: Assign User and Onboard Computer" (Ginko IT) that this gap register entry is migrating.

This ticket is item 20 of the Rewst → MSPbots migration gap register (`mspbots-gap-register.xlsx`). It names a single missing capability on an existing connector: `immybot_computers_set_primary_user`, to assign a `primaryPersonId` to a computer (and optionally `onboardingStatus`, `additionalPersonIds`). The ticket's own verification note says "ImmyBot 已连接，68 个工具 ... 描述逐条核对无对应；computers_* 全部只读" — i.e. the reporter already checked the live tool list and found the Computers tool group read-only. ## Product design

### Goals / Non-goals

**Goals**
- Add one new tool, `immybot_computers_set_primary_user`, that assigns (or replaces) a computer's primary person, matching ImmyBot's `PUT /api/v1/computers/{id}` endpoint named in the ticket.
- Let the same call optionally set `onboardingStatus` and `additionalPersonIds` in one round trip, matching the ticket's "可同时设 onboardingStatus 和附加用户".
- Keep the result visible to the calling agent: return the updated computer record (so the agent can confirm `primaryPersonId` actually changed), not just a bare success flag.
- Follow this repo's existing conventions for a metadata-changing write tool (annotation, error envelope, navigation listing, description budget) with no new dependency.

**Non-goals**
- **No persons/people lookup tool.** The ticket's own example assumes `immybot_persons_list` exists to resolve a `Person id`, but no such tool, module, or vendor API path is evidenced anywhere in this repository (see Current state). Adding a persons tool group is a separate, larger ask with its own vendor-endpoint research — out of scope here. See Open questions for how a caller is expected to get a person id today.
- **No `providerLinkUpdates` parameter surface.** The ticket lists it as an optional array field on the endpoint but gives no schema for its items, and the ticket's own real Rewst example sends it as a fixed empty array (`"providerLinkUpdates":[]`), never populated. This design reproduces that proven shape (always send `[]`) rather than inventing an unevidenced sub-schema as a tool parameter.
- **No `tenantId` parameter.** Listed as optional on the endpoint, but the ticket's own working Rewst example does not send it in the body at all (only `id` as a path parameter, which this tool already has as `computerId`). Not exposing it avoids a caller passing a tenant id that disagrees with the computer's actual tenant.
- Not changing any other Computers tool, and not touching `immybot_computers_create` (still unsupported, unrelated to this ask).

### Acceptance criteria

- **AC1**: Given a computer id and a valid person id, When an agent calls `immybot_computers_set_primary_user(computerId=<id>, primaryPersonId=<id>)`, Then the tool issues `PUT computers/{id}` with a body containing `primaryPersonId` and `providerLinkUpdates: []`, and returns the updated computer record (including the new `primaryPersonId`) — not just a bare `{"done": true}`.
- **AC2**: Given `onboardingStatus` is also passed, When the tool is called, Then the outbound request body includes `onboardingStatus` with that exact value, and it is not silently dropped.
- **AC3**: Given `additionalPersonIds` is also passed, When the tool is called, Then the outbound request body includes `additionalPersonIds` as a list of integers.
- **AC4**: Given neither `onboardingStatus` nor `additionalPersonIds` is passed, When the tool is called, Then the outbound body omits both keys entirely (no `null` values sent) — same `compact()` convention this repo already uses elsewhere (e.g. `computers.py:68-75`).
- **AC5**: Given an invalid `computerId` or `primaryPersonId` (ImmyBot returns a 4xx), When the tool is called, Then the call does not raise an unhandled exception and does not report success; the structured error envelope carries ImmyBot's literal status/message, the same as every other tool in this repo.
- **AC6**: Given the tool's registered description (as returned by `tools/list`), When it is read, Then it says what the tool changes (the computer's primary person / linked users / onboarding status), that it should be called only when the user explicitly asks, and that the caller must already know the target person's id (this tool has no way to look one up) — so the calling agent doesn't assume a lookup tool exists.
- **AC7**: Given `computerId` or `primaryPersonId` is omitted, When the tool is called, Then the MCP framework rejects the call (missing required parameter) before any HTTP request is made to ImmyBot.

### Open questions

- **[Not blocking, assumption]** There is no `persons`/`people` list or search tool anywhere in this MCP server, and no evidence of such a vendor endpoint in this repo's code, tests, or README. The ticket's own Rewst example resolves `primaryPersonId` via a Rewst-side context variable (`{{ CTX.immy_person_select }}`), not via a tool call to this MCP. This design assumes the calling agent/workflow already has the target person's id from elsewhere (e.g. from `immybot_computers_get`'s `includePrimaryPerson` data on a computer the person is already linked to, or from the identity/onboarding system that drives the request) — it does **not** add a persons lookup tool. If an agent genuinely needs to search for a person by name/email with no prior id, that is a new, separate ask (a "persons" tool group) and should be filed as its own gap-register item once a concrete ImmyBot persons/people API path is confirmed.
- **[Not blocking, assumption]** `onboardingStatus`'s legal values are undocumented anywhere in this codebase. The tool accepts it as a free string and lets ImmyBot's own validation reject bad values (surfaced through the existing error envelope, AC5) rather than this design guessing an enum with no evidence.
- **[Not blocking, assumption]** `tenantId` and a structured `providerLinkUpdates` are in the ticket's endpoint description but not in its one real usage example; this design follows the proven example (see Non-goals) instead of the fuller, unevidenced schema. If a concrete need for per-provider link updates shows up later, extend the tool then with real evidence of the item shape.
- **[Not blocking]** No ImmyBot test tenant/credentials are available in this sandbox. Automated tests use this repo's existing fake-HTTP-recorder pattern (`tests/test_api_client.py`, same approach as PRD-21665); any live-instance verification is recorded as "needs a real vendor account" per `mcp-track.md` §2.5/§3, which does not block `6b`.

## Tech design

### Conclusion

Add one new tool, `immybot_computers_set_primary_user`, to the existing `computers.py` tool group, following the same `register()` / `run_tool()` pattern as every other tool in this file. It calls the already-implemented but previously-unused `ImmyBotClient.put()` (`api_client.py:177`) against `computers/{id}` with a body built from `primaryPersonId` (required) plus `onboardingStatus` / `additionalPersonIds` (optional, `compact()`-ed) and a fixed `providerLinkUpdates: []`. Annotated `WRITES_IDEMPOTENT` (no `confirm` gate) — same category as the existing `immybot_computers_trigger_checkin` (`computers.py:159`) and `immybot_deployments_create`, both metadata/config changes that this repo does not gate behind `confirm` (see Option analysis). No new dependency, no DB (this repo has none), one new small type (`PersonId`).

### Data & API contract

- **Outbound request** (ImmyBot API, path from the ticket: `PUT {Immy instance}/api/v1/computers/{id}`, via `ImmyBotClient.put()` at `api_client.py:177-178`, which the shared `request()` method resolves against `self.base_url` — unchanged base-url handling):
  - Always: `{"primaryPersonId": <int>, "providerLinkUpdates": []}`
  - Plus, only when given: `"onboardingStatus": "<string>"`, `"additionalPersonIds": [<int>, ...]`
  - Example (matches the ticket's own Rewst example, adding the id path param as `computerId`): `PUT computers/42` with body `{"primaryPersonId": 7, "providerLinkUpdates": []}`.
- **MCP tool contract (new)**: `immybot_computers_set_primary_user(computerId: int, primaryPersonId: int, onboardingStatus?: string, additionalPersonIds?: int[]) -> str` — a JSON-encoded updated computer record (id, primaryPersonId, agents[], and whatever other fields `computers/{id}` returns minus `inventory`), or the structured error envelope from `error_envelope()` on failure (same shape as every other tool, `_common.py:237-264`).
- **Error surfacing** (unchanged mechanism): an ImmyBot 4xx (e.g. unknown `computerId` or `primaryPersonId`) becomes an `invalid_argument` / `not_found` envelope carrying the vendor's literal message (`api_client.py:243-245,292-316`), per AC5.
- No DB, no migration, no new credential fields — this repository has no database and this tool needs no new ImmyBot credential beyond the four headers every tool already requires.

### Key flow / sequence

1. Agent calls `immybot_computers_set_primary_user(computerId=42, primaryPersonId=7)`, optionally with `onboardingStatus` / `additionalPersonIds`.
2. The tool builds the body: `{"primaryPersonId": 7, "providerLinkUpdates": []}`, merged with any optional fields present (`compact()`).
3. `client.put("computers/42", body)` → ImmyBot updates the computer's primary person (and onboarding status / additional users, if sent).
4. ImmyBot returns the updated computer object.
5. The tool returns `names(drop(record, "inventory"))` — enum values normalized, inventory omitted (consistent with `immybot_computers_get`) — so the agent can see the new `primaryPersonId` took effect.
6. On any ImmyBot 4xx/5xx, `run_tool()`'s existing exception handling turns it into the standard error envelope (unchanged, `_common.py:237-264`).

### Non-functional

- **Idempotency/concurrency**: `PUT` with the same `primaryPersonId` repeated produces the same end state — genuinely idempotent, matching the `WRITES_IDEMPOTENT` annotation. The underlying HTTP client only retries GETs and 429s (`api_client.py:228-233`), so a PUT is never silently replayed by this client on a transient failure.
- **Performance**: single synchronous HTTP call, no pagination, no new timeout considerations beyond the default request timeout already used by every other write tool in this file.
- **Security**: no new credential type; headers-only auth is unchanged (`server.py` middleware, `api_client.py`). No secret-shaped fields are involved in this tool's parameters or response (unlike task parameters elsewhere, which already go through `mask_parameters()` — not needed here since nothing in this payload matches `_SECRET_NAME`, `_common.py:104`).
- **Multi-tenant isolation**: unaffected — `computerId` and credentials continue to flow per-request exactly as every other tool; this tool does not accept or forward a `tenantId` body parameter (see Non-goals), removing one way a caller could (even accidentally) reference the wrong tenant's data.
- **Observability**: reuses the existing `run_tool()` logging (`tool=%s outcome=... ms=%d`, `_common.py:261`) and `ImmyBotClient.request()`'s per-call log line (`api_client.py:220-223`) — no new logging needed, and (per the existing convention) no request/response bodies are logged.
